## 1. Purpose and Scope

Article 12 of the EU AI Act requires that high-risk AI systems be designed and developed with automatic logging capabilities to ensure traceability throughout the system's operational lifetime. Logs must be sufficient to enable post-hoc monitoring of the system's operation and to support investigation of incidents.

This document describes SignalPath's logging architecture for SP-AI-001 SignalPath Interpret, covering the categories of events logged, log integrity and retention, access controls, and the use of logs in incident investigation — including the documented incident SP-INC-2026-001.

---

## 2. Logging Architecture

SP-AI-001 generates logs at four levels:

| Log Level | Description | Generated By |
|---|---|---|
| Session logs | Per-call operational record | System (automatic) |
| Confidence score logs | Per-segment SIMCS telemetry | System (automatic) |
| Threshold and guardrail event logs | Automated alerts and guardrail action records | System (automatic) |
| Governance and audit logs | Human actions, overrides, escalations, and reviews | System (human-triggered, automatic record) |

All log categories are generated automatically. No log entry requires human initiation to be created, though human actions (overrides, escalations, suspensions) generate automatic records of those actions.

---

## 3. Log Categories and Content

### 3.1 Session Logs

A session log is created for every call processed with SP-AI-001 involvement. Session logs capture:

| Field | Description |
|---|---|
| Session ID | Unique identifier for the call session |
| Timestamp — start | Call initiation time (UTC) |
| Timestamp — end | Call termination time (UTC) |
| Call type classification | Standard relay, emergency (exclusion applied), or escalated |
| Interpreter ID | Anonymised identifier of the assigned interpreter |
| AI assistance status | Active / suspended / excluded (emergency) |
| Session-level SIMCS | Aggregate confidence score for the session |
| Threshold events | Count of threshold breach events during the session |
| Human override events | Count of interpreter override actions |
| Escalation flags | Any P1 or P2 escalation triggered during the session |

Session logs do not contain raw video data. Raw video is not retained beyond call duration. Session logs contain only derived operational metadata.

### 3.2 Confidence Score Logs

Per-segment SIMCS logs are generated continuously during AI-assisted sessions. These logs capture:

| Field | Description |
|---|---|
| Session ID | Links to session log |
| Segment timestamp | Time of segment generation (UTC) |
| SIMCS value | Confidence score for the segment (0–100) |
| Threshold state | Normal / elevated / breach / critical |
| Output delivered | Whether the segment was relayed by the interpreter (yes / no / modified) |

Confidence score logs are the primary data source for demographic monitoring and drift detection. The SP-INC-2026-001 skin tone disparity was identified by analysing SIMCS distributions across demographic groups using confidence score log data.

### 3.3 Threshold and Guardrail Event Logs

Every threshold breach and automated guardrail action generates an event log entry. These are the highest-priority log entries for compliance and incident investigation purposes.

| Event Type | Fields Logged |
|---|---|
| Elevated monitoring state (SIMCS 80–84%) | Session ID, timestamp, SIMCS value, interpreter notified |
| Threshold breach (SIMCS < 80%) | Session ID, timestamp, SIMCS value, escalation triggered, Operations Manager notified |
| Critical exception (SIMCS < 75%) | Session ID, timestamp, SIMCS value, AI overlay suspended, automated guardrail actions executed, response SLA started |
| Emergency call exclusion | Session ID, timestamp, call type classification, AI exclusion confirmed |
| System-wide suspension | Timestamp, authorising officer, affected sessions, duration |

For critical exception events, the full guardrail action log is captured, including:
- Guardrail action description
- Automated notifications sent
- Incident escalation log ID
- Response SLA deadline
- Audit trail entry reference

### 3.4 Governance and Audit Logs

Human governance actions generate automatic audit log entries. These cover:

| Action | Fields Logged |
|---|---|
| Interpreter override | Session ID, timestamp, interpreter ID, segment overridden, reason code |
| Operational suspension | Timestamp, authorising officer, scope, duration, reason |
| Risk register update | Timestamp, AGPO officer, risk ID, change summary |
| Conformity pack update | Timestamp, document version, author, change summary |
| Post-incident review completion | Incident ID, review date, findings summary, corrective actions |
| Governance Committee review | Meeting date, attendees, agenda items, decisions |

## 4. Log Integrity

### 4.1 Tamper Evidence

Log entries are written to an append-only log store. Once written, log entries cannot be modified or deleted through any operational interface. Deletion requires a documented retention policy action and is itself logged.

Log integrity is verified through:
- Cryptographic hashing of log entries at write time
- Periodic integrity checks comparing stored hashes against log content
- Anomaly detection on log completeness (gaps in session log continuity trigger alerts)

### 4.2 Access Controls

| Role | Access Level |
|---|---|
| VRS interpreter | Read access to own session logs only |
| Operations Manager | Read access to all session and guardrail event logs |
| AI Governance Program Office | Full read access to all log categories |
| Engineering | Full read access; write access limited to system-generated entries only |
| General Counsel | Read access to all logs for legal and regulatory purposes |
| External auditor | Read access granted on a per-engagement basis, scoped to the audit requirement |

Write access to logs is restricted to automated system processes. No human user has write access to operational log entries.

## 5. Log Retention

Log retention schedules are aligned with the data retention policy documented in Document 03 (Data Governance) and with Article 12(1) requirements for logs to be kept for the period appropriate to the purpose.

| Log Category | Retention Period | Basis |
|---|---|---|
| Session logs | 24 months | Compliance and audit; performance monitoring baseline |
| Confidence score logs | 24 months | Demographic monitoring; drift detection |
| Threshold and guardrail event logs | 24 months (standard); 5 years (incident-linked) | Legal obligation for incident-linked records |
| Governance and audit logs | 5 years | Legal obligation; regulatory submission readiness |
| Incident investigation records | Duration of investigation + 5 years | Legal obligation |

Logs linked to an open corrective action or regulatory enquiry are retained until the matter is closed, regardless of the standard retention period.

## 6. Incident SP-INC-2026-001 — Logging in Practice

Incident SP-INC-2026-001 (SP-AI-001 Skin Tone Accuracy Disparity) demonstrates the logging architecture functioning as designed.

**Detection:** The incident was detected through demographic monitoring of confidence score logs in the Command Center. Aggregate SIMCS metrics did not show the disparity. Stratified analysis of per-segment confidence score logs by demographic group revealed a systematic gap correlated with skin tone.

**Traceability:** Confidence score logs enabled the AGPO to:
- Identify the affected session types and time period
- Quantify the confidence gap by demographic group
- Trace affected calls to the relevant training data period
- Provide the AI Governance Committee with a complete picture of scope and impact

**Corrective action audit trail:** All corrective actions taken following SP-INC-2026-001 — including the training data audit, the demographic coverage target for v1.1, and the expanded demographic monitoring in the Command Center — are recorded in governance and audit logs with named owners and completion timestamps.

**Root cause:** Root cause analysis used confidence score logs and training data provenance records to confirm that the disparity originated in training data composition rather than in inference-time processing. This distinction — provenance traceability from inference back to training data — is the reason training data provenance documentation (Document 03) and logging (this document) are designed to work together.

## 7. FCC Part 64 Compliance Logging

FCC Part 64 imposes functional equivalency obligations on VRS providers. Logging requirements under Part 64 include records of service continuity, interpreter assignment, and call handling. SP-AI-001's session logs satisfy Part 64 record-keeping requirements for AI-assisted calls, with the following additional records:

- AI assistance status per call (ensuring that any call with AI involvement is distinguishable from human-only calls in the compliance record)
- Emergency call exclusion confirmation per relevant call
- Threshold breach and human override events (demonstrating that functional equivalency safeguards were active)

FCC Part 64 compliance logs are maintained separately from EU AI Act audit logs and are made available to the FCC on request.
